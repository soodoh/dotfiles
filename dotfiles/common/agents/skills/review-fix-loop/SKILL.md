# Review-fix loop

`/skill:review-fix-loop origin/main...HEAD`

The parent owns coverage, finding dispositions, validation, and operator decisions. Invocation authorizes in-scope fixes and their local commits on the requested branch in a trusted checkout. Run at most five review rounds, including the initial review, staged-candidate reviews, and any risk-triggered second look. A round can cover multiple lanes on one tree. The cap prevents another review, not preparing and validating a fix. Use one writer at a time. No amend, push, PR changes, merge, or history rewrites.

## Pin the range

1. Require an explicit `A..B` or `A...B` with both endpoints. Resolve each endpoint to a commit (`git rev-parse --verify --end-of-options "${ref}^{commit}"`, each ref as one argument). For `A..B`, pin `A` as baseline. For `A...B`, pin the unique `git merge-base --all "$left" "$right"` result. Ask for a corrected range if resolution fails or there is no unique merge base. Keep the original baseline throughout.
2. Record the repository root, attached target branch, baseline SHA and expected tip (initially `B`). Require the target branch at the expected tip, no Git operation in progress, and an empty `git status --porcelain=v1 --untracked-files=all --ignore-submodules=none` before the first pass and all subsequent review or write handoffs except an inspected [staged candidate](#gate-high-impact-fixes) or recovery handoff. Use [recovery](#recover-the-affected-step) for a mismatched or dirty checkout. Check the net diff with `git diff --quiet --no-ext-diff --no-textconv --ignore-submodules=none "$base" "$tip" --`: status 0 means there is nothing to review, 1 means continue, and any other status requires diagnosis. After a fix that makes the cumulative diff empty, still review the fix delta if the cap permits.
3. Follow [Pinned review inputs](review-inputs.md) to freeze the trusted guidance, select a neutral launch directory, and supply Git-object evidence to read-only children. Resolve the pinned `code-review-expert` rubric and checklists and the trusted `pi-subagents` launch guidance. If a required capability is absent, report it; do not silently substitute another executor.
4. Write a short intent brief: intended behavior, its source (operator request, requirement, test, or documented contract), and contracts that must remain unchanged. Explicitly assign consequential contracts to a review lane and add newly discovered ones to the coverage record. Distinguish inferred intent from known requirements and mark unknowns. Give the relevant brief to each reviewer and the writer. If competing interpretations would lead to different fixes, ask the operator before changing that behavior; continue independent work where safe.

## Select and launch children

- Call `review_loop_models` before each launch or parallel wave. It filters the live registry using Pi's effective `enabledModels` and session scope. It reads recorded Copilot premium usage and the highest recorded relevant window among enabled CLIProxyAPI Codex accounts without refreshing the cache. Stale or expired values count; missing values do not block; recorded usage at or above 95% excludes that provider. Google Vertex has no quota gate. This is a preflight, not a reservation. Use only returned eligible models that meet project/provider restrictions.
- Rank by role and task risk, not by round number. Prefer a strong model at `high` for broad discovery, hard fixes, or wide verification; a capable model at `medium` for routine writing or targeted verification. Respect explicit role preferences, supported levels, and configured thinking limits. For an independent second opinion prefer a different family when it is a good fit, not a different provider serving the same family. Default to the current model for serious review when it fits and is eligible. Pin the exact `provider/id:level` and record the effective model and effort from each run when available.
- Launch native async workflows: one fenced `js workflow` block with `subagent({ workflow: true, async: true, cwd, args, worktree: false, options: { context: "fresh", agentScope: "user" } })`, where `cwd` is the neutral launch directory. Use awaited `runs.run` or `runs.all` with stable, distinct keys and the [pinned launch boundary](review-inputs.md#pin-the-rules-once). Give each child the repo identity, exact refs, pinned inputs, authority, completion criteria, and output shape. Return per-child results and run IDs. Native completion wakes the parent; do not poll. If only the reply block is missing and nothing launched, retry with the same boundary and `options.script: source`, omitting `workflow`.

## Review the exact tree

1. **Cumulative discovery:** Review `original base → current target` on the initial round and after each batch of material fixes. Give fresh read-only `reviewer` children the intent, pinned rules, full patch, and scoped source evidence. Ask what is wrong with the full net change, including areas the batch did not touch. Withhold earlier findings and verdicts until discovery is complete; apply the parent’s findings ledger afterward.
2. **Fix verification:** For a fix batch, also assess `pre-fix tip → same target` against the accepted findings and focused check results. Verify the fixes, look for regressions in their blast radius, and reassess affected open findings and gaps. Expand scope when a shared contract changes or coverage is invalidated. Discovery and verification can share a round in separate lanes or with the verification brief supplied after discovery. A [staged gate](#gate-high-impact-fixes) can cover both. If the cumulative diff is empty, record that from Git and still verify the fix delta.
3. **Large-diff exception:** Map a large or mixed diff (~500 changed lines is a planning cue) into a small wave of behavior or risk lanes. Assign shared contracts and cross-slice behavior explicitly; give each lane access to the full patch and [pinned source](review-inputs.md#serve-evidence-by-git-object). If repeating cumulative discovery is impractical even with lanes, record why, use targeted verification between batches, and reserve a round for cumulative discovery on the final tree. The reserved round may also serve as a gate if it covers both tasks. Never count a delta-only pass as cumulative coverage. Page through truncated reads or split unread scope rather than silently dropping it.
4. **Accept results:** Have reviewers use the pinned expert rubric and relevant checklists, not its workflow or output template. Require target SHA, complete or partial coverage of the assigned behavior (including the contracts actually assessed), findings or explicit no findings, and validation limits. Findings include file/line, impact, severity, smallest fix, and evidence for [triage](#triage-and-prepare-fixes). Gaps name the missing scope and evidence needed; an unrun check is a gap only if needed for a material assessment. Recheck the checkout, preserve usable sibling results, and clarify once or assign a narrower repair pass for accessible evidence. Continue with independently verifiable fixes; keep remaining gaps open.

## Triage and prepare fixes

1. Keep a findings ledger across rounds with stable IDs based on cause and behavior, not line numbers. Record each disposition, evidence, and target tree. Deduplicate across lanes and rounds; reopen rejected or deferred findings only on materially new evidence. Before assigning a fix, record: **What condition reaches the problem at the current tip? What contract does it violate? What change in this range introduced it or made it reachable?** Use source and caller evidence, documented contracts, or focused checks. For a disputed or high-impact finding, ask a fresh read-only reviewer to try to disprove it. Unverified findings stay open with the evidence needed to resolve them; they are not writer tasks. Defer polish, discretionary refactors, and out-of-scope work.
2. If no eligible work remains, apply [stopping criteria](#decide-when-to-stop). Otherwise batch the verified material findings and start a separate fresh `worker` with the accepted IDs and their evidence, minimal scope, expected branch/tip, and validation plan. Mark a batch for the [pre-commit gate](#gate-high-impact-fixes) if it fixes a high-impact issue (e.g. data loss or an authorization boundary) or changes a shared contract. Keep independently eligible narrow fixes separate if the gate would otherwise block them. The writer rechecks checkout state and confirms the premise before editing. If it needs a decision, it pauses before further affected writes or commits and uses `contact_supervisor` with `need_decision`; the parent resolves it or asks the operator. If the channel is unavailable, return the evidence and preserve partial work.
3. Choose a focused check that exercises the violated contract. When practical, require the same check to fail for the expected reason on the **pre-fix tip** and pass on the candidate. Use an isolated checkout for the pre-fix run if needed. For declarative changes, prefer an independent schema or invariant check when it gives better evidence than a new test. If a before/after check is impractical, record why and what source evidence or other check distinguishes the fix from the bug. Do not weaken assertions or substitute a passing check that never exercised the failure.
4. The writer stages only approved changes, inspects the staged diff with `--ignore-submodules=none`, and requires no unstaged or untracked changes or dirty submodules. Pin the candidate with `git write-tree`, run the planned validation, then recheck the index tree and checkout. If the batch needs the gate (including risk the writer discovers while fixing), return without committing: branch, pre-fix tip, tested tree SHA, addressed IDs, staged files, and check commands and results. Otherwise proceed to [commit verification](#commit-and-verify).

## Gate high-impact fixes

1. The parent inspects the staged scope and confirms the writer has stopped, the branch and tip are unchanged, no Git operation is in progress, the staged tree matches the tested SHA, and there are no unstaged or untracked changes or dirty submodules. Repeat these checks before accepting the gate result or handing the candidate to a writer. A mismatch goes to [recovery](#recover-the-affected-step), not commit.
2. Use the next round for independent read-only [fix verification](#review-the-exact-tree) on the staged tree. Include cumulative discovery in that round by default. The parent supplies [pinned source artifacts](review-inputs.md#serve-evidence-by-git-object); reviewers do not run Git. Require the exact tree SHA and evidence that the accepted fixes resolve the findings, introduce no observed material regressions, and leave no material gap in that assessment.
3. If the gate cannot pass within budget, leave the candidate uncommitted and report its staged state, validation, and blocker. A changed candidate needs fresh validation and a new round before commitment. If the gate passes, resume the eligible writer or appoint a replacement for a commit-only handoff pinned to the approved tree. Triage any independent findings from the pass on the verified tip; only reuse coverage for the exact tree assessed.

## Commit and verify

1. Before committing, the writer rechecks the candidate's passing checks, index tree, status, branch, and tip. If gated, the index tree must match the independently reviewed SHA. Commit a nonempty change using normal hooks and project conventions. Return the commit SHA, tested tree SHA, addressed IDs, files, and check commands and results, or the exact blocker and checkout state.
2. The parent checks that the resulting tip is on the expected branch, the commit's only parent is the expected pre-write tip, the diff contains only approved fixes/tests, and the checkout is clean. For a bounded fix-forward recovery, verify each new commit's parent and permitted scope in order. Compare `git rev-parse --verify "${commit}^{tree}"` to the tested tree. If they differ (e.g. an in-scope hook edit), rerun the affected checks on the actual clean committed tree. For a gated batch, apply the same gate criteria to independent fix verification on the changed tree within the remaining round budget; include cumulative discovery as for any gate. If the committed tree lacks required evidence, report the commit as unverified and stop; do not advance the expected tip.
3. Once verified, record the fix and advance the expected tip. Reuse fix verification and cumulative discovery from the gate only for the scopes completed on the exact committed tree. If either is still needed, schedule it with the remaining budget, subject to the large-diff exception. If the cap prevents review, report the coverage actually obtained.

## Decide when to stop

1. Before a clean stop, require complete cumulative discovery on the exact final tree, completed fix verification if applicable, and no unresolved material findings or coverage gaps. If the latest round was delta-only, use the reserved cumulative round. Triage its results normally. If budget or evidence runs out, stop with the limits stated; in a partial review say no actionable findings **in the assessed scope**, not approval.
2. **Risk-triggered second look:** Before stopping with no eligible fix, check whether the diff changes a consequential contract (e.g. authorization, deletion, or public API compatibility) that only one reviewer assessed on the exact final tree. Use at most one remaining round per run for a fresh, targeted second opinion on such contracts. Give it concrete contract questions and pinned evidence, not the first reviewer’s verdict. Skip a contract if another independent reviewer assessed it on that tree (including a matching pre-commit gate), or a focused CI check or human review on that tree provides evidence for that specific risk. Generic green CI or a second lane on unrelated code does not count. If the round is unavailable or the second look cannot assess the contract, report the missing check and why. Triage new findings normally and recheck final-tree evidence after any resulting fix, without launching a second risk-triggered round.
3. Otherwise stop without repeating a completed review of an unchanged tree. Confirmed coverage and passing checks are evidence, not merge approval.

## Recover the affected step

- **Dirty checkout or moved tip:** Inspect status, refs, and ownership. Keep others' changes untouched. Continue pinned review or validation in an isolated clean checkout when safe; this does not authorize moving the target branch or integrating from the isolated checkout while the target is blocked. Resume known loop-owned partial writes only after inspecting the staged/unstaged diff against accepted IDs. Ask before including or removing unrelated changes, using a different target tip, or proceeding with external state that could affect the result. Do not silently switch branches, stash, reset, or bypass a Git operation in progress.
- **Failed checks, hooks, or Git verification:** Diagnose the failure; fix an in-scope defect and rerun affected checks. Compare with the pinned baseline where needed to distinguish a regression from an existing failure. Retry a plausible transient failure once; do not waive required checks or bypass hooks. If an in-scope defect is already committed, fix forward with a verified local commit on the expected tip, not a rewrite. Ask before expanding scope, changing intended behavior, or waiving a requirement. Treat unexplained ancestry/content as external until verified.
- **Launch or runtime failure:** Stop the failed attempt, report the exact error and run/checkout state, and ensure no competing writer is active. Verify a clean checkout or capture and inspect the partial diff before another attempt. Correct a recoverable setup error or retry a transient failure once through the same Pi protocol. On a model/provider-specific failure, refresh the **eligible candidate list only** (no usage refresh) and explicitly launch the next eligible model that fits; do not silently retry the same failed model indefinitely, bypass a permission boundary, or switch executors. Keep valid completed lanes and retry only missing work. Resume an existing writer only if its resolved model is still eligible for the retry; a replacement writer needs the inspected checkpoint and the same edit boundary.
- **Bound recovery per step:** Keep failure signatures and attempted candidates. Give each transient signature one retry and each model one fallback attempt (plus its transient retry if justified). Allow up to two corrective attempts for in-scope validation failures in a round; an unchanged failure with no new evidence ends recovery sooner. Recovery, clarification, and repairing incomplete coverage at the same target do not count as new review rounds. Escalate only decisions or access that need the operator; otherwise stop only when there is no safe, in-scope path left. Preserve and report any partial work or unverified commit.

## Final summary

- **Fixed:** Net fixes, short verified commit SHAs, and checks that passed. Say if no fixes were committed and verified.
- **Stopped:** Review count and reason; distinguish cumulative discovery, fix verification, and any risk-triggered check or missing check on the exact final tree. If the final commit was validated but the fix delta on its exact tree was not independently reviewed, say **Final commit validated; not independently re-reviewed.**
- **Manual follow-up:** Unresolved or deferred findings and gaps, with what would close each. Include any uncommitted work, unverified commit SHA, and the specific blocker. Do not infer approval from the cap or from missing coverage.
