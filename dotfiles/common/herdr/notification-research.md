# Herdr clickable-notification audit

Subsequent configuration decision: the official Pi reporter is now vendored in
[`pi-extensions`](../../../pi-extensions/packages/herdr-agent-state/README.md), and
alerter is declared in the existing Homebrew task. The audit below predates those
changes; the notification plugin is still not installed. See also the later
[mise plugin-management research](plugin-management-research.md).

## Recommendation

**Useful macOS notification delivery, but not exact old tmux click-routing parity.** `herdr-focus-notify` can activate Ghostty **the application** and focus the agent’s Herdr workspace/tab/pane on the originating server. It cannot identify the correct Ghostty **window**, Ghostty tab/surface, attached Herdr client, or Pi session. Adopt only with that explicit tradeoff (prefer a single Ghostty/Herdr window); exact multiwindow parity requires additional routing implementation, not a configuration switch.

Parent’s read-only comparison of the deleted helper at repository HEAD confirms the lost behavior: it explicitly selected/switched a Ghostty tmux client, focused a Ghostty terminal by AppleScript ID, opened an attach client when necessary, and checked server PID. The plugin does none of those things.

Installation can be reconciled by a small, macOS-scoped **mise task**, but `herdr plugin install` itself is not no-op-idempotent. Keep installation separate from explicit upgrades and retain user runtime state. No installation, compilation, notification tests, configuration changes, session controls, or repository edits were performed in this audit.

## What a click actually does

- A `pane.focused` event learns the **frontmost bundle identifier**, via AppleScript/System Events, into `terminal-memory.json`, keyed only by workspace. Any app/terminal/IDE can be learned; Ghostty, kitty, iTerm2, Terminal, WezTerm, etc. receive the same generic app activation, not terminal-specific window control. A programmatic focus while another app is frontmost can mis-bind that app. No binding means no app activation.
- At notification creation, the plugin generates a shell script containing the then-learned app and pane ID. Successful alerter output `Focus`, `@ACTIONCLICKED`, or `@CONTENTCLICKED` invokes **`open -b <bundle>` followed by `herdr agent focus <pane>`**. Activation failure is ignored. Pending scripts retain their captured app even if a later focus learns a different one.
- Herdr supplies `HERDR_SOCKET_PATH` and its executable path to hooks; detached scripts inherit them. Thus normal hook-driven focus targets the **originating server/session socket**, not merely whichever server is the default at click time. Herdr focuses the target workspace/pane and its containing tab; there is no attach/resume/reconnect operation or Pi-session identity check. A stopped/replaced server or closed/reused pane is not handled with durable identity validation.
- Shared state is **not server-namespaced**: terminal bindings use workspace IDs, script names hash pane IDs, and alerter groups sanitize pane IDs. Different Herdr sessions/servers with overlapping IDs can replace/clear notifications or bindings. No client/window ID exists in the routing.
- Visibility suppression checks Herdr’s pane-focused flag plus frontmost **app**, not actual window visibility. Another Ghostty window frontmost can incorrectly suppress notification. Manual focus clears a pending group; a two-second monitor sometimes clears it on returning to the app. Default timeout is 3600 seconds.

Sources: [focus detection](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/src/focus.rs), [generated click script](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/src/script.rs), [state](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/src/state.rs), [Herdr hook environment](https://github.com/herdrdev/herdr/blob/v0.8.2/src/app/api/plugins/runtime.rs), [Herdr pane focus](https://github.com/herdrdev/herdr/blob/v0.8.2/src/app/agents.rs).

## Events, Pi needs-input, and duplicate notifications

Only `pane.agent_status_changed` statuses **`blocked` / `done`** produce notifications; `pane.focused` learns/clears. This is not an independent detector or a Pi lifecycle adapter. Notifications contain generic status-specific copy and a bundled agent icon, not transcript summaries or session names. Herdr can emit this event for presentation changes as well as status changes, so this is not precisely one alert per turn. [Event parser](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/src/event.rs), [event emission](https://github.com/herdrdev/herdr/blob/v0.8.2/src/app/api.rs).

**Important Pi limit:** official v0.8.2 Pi integration reports working/idle from lifecycle events and blocked from explicit `herdr:blocked` events. Active `herdr:pi` full-lifecycle authority suppresses screen/manifest fallback, including visible-blocker overrides. The notifier cannot recover a needs-input prompt that the authoritative Pi reporter never marks blocked. Pi integration/package choice remains a separate ownership decision, not a notifier requirement: parent verified official installation writes the embedded reporter to Pi’s runtime extensions directory; vendoring can work but shifts provenance/updates to dotfiles, is invisible to integration status when package-only, and must not be combined with an installer that could overwrite a tracked symlink target. No integration changes were made here. [Official Pi reporter](https://github.com/herdrdev/herdr/blob/v0.8.2/src/integration/assets/pi/herdr-agent-state.ts), [authority classification](https://github.com/herdrdev/herdr/blob/v0.8.2/src/detect/mod.rs), [authority precedence](https://github.com/herdrdev/herdr/blob/v0.8.2/src/terminal/state.rs).

Plugin delivery is independent of Herdr native notifications and does not disable them. With the plugin adopted, use `[ui.toast] delivery = "off"` (or `"herdr"` for internal-only toasts) to avoid duplicate desktop alerts; review any separate Pi notifier independently. Herdr terminal delivery supports Ghostty/iTerm2/WezTerm OSC 9 and kitty OSC 99, but those sequences do not implement this plugin’s pane-focus callback. [Toast delivery](https://github.com/herdrdev/herdr/blob/v0.8.2/src/server/notifications.rs), [configuration](https://github.com/herdrdev/herdr/blob/v0.8.2/src/config/model.rs), [terminal notifications](https://github.com/herdrdev/herdr/blob/v0.8.2/src/terminal_notify.rs).

## Alerter/platform and permissions

Plugin is macOS-only. It **does not install alerter** or fall back to terminal-notifier/native notifications: it searches executable `alerter` in PATH, then `/opt/homebrew/bin`, `/usr/local/bin`, and `~/.local/bin`; missing dependency returns an installation hint. It validates executability, **not version or provenance**; a stale PATH binary can shadow Homebrew. [Resolution/delivery](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/src/notifier.rs).

Current alerter **26.5** source (`57b5d7dee3895974776c42e45102d5fd975c521b`) and README require **macOS 13+**. Plugin double-dash arguments match the v26 Swift CLI; stdout handling matches `Focus` / `@ACTIONCLICKED` / `@CONTENTCLICKED`, with exit 0 on interaction. Old single-dash-era alerter is not the supported target. Plugin supplies neither `--json` nor `--sender`; alerter defaults sender to `com.apple.Terminal`. **Do not “fix” Ghostty routing by adding `--sender com.mitchellh.ghostty`: upstream warns sender impersonation launches that app on click instead of alerter.** Default-sender interaction/focus ordering still needs real macOS validation; static callback compatibility does not prove OS notification behavior. Plugin uses local bundled icons; alerter’s app-icon support uses private APIs that may break. [README](https://github.com/vjeantet/alerter/blob/57b5d7dee3895974776c42e45102d5fd975c521b/README.md), [CLI](https://github.com/vjeantet/alerter/blob/57b5d7dee3895974776c42e45102d5fd975c521b/Sources/Alerter/AlerterCommand.swift), [output](https://github.com/vjeantet/alerter/blob/57b5d7dee3895974776c42e45102d5fd975c521b/Sources/Alerter/OutputFormatter.swift).

**No Herdr permission sandbox exists here.** Plugin manifest declares arbitrary build/startup/action/event commands, not scoped permission grants; v0.8.2 manifest schema has no permissions field. Install confirmation/`--yes` is trust acceptance, not a capability restriction. Cargo build/dependency build scripts and runtime processes execute with user privileges and inherited environment; runtime receives the Herdr API socket, allowing much more than focus. Builds scrub Herdr-specific runtime variables, not general secrets. Source pinning does not sandbox code. AppleScript frontmost-app lookup and macOS notification authorization may require user approval; exact TCC prompts were not exercised, and no permission grants were changed. [Manifest loader](https://github.com/herdrdev/herdr/blob/v0.8.2/src/app/api/plugins/manifest.rs), [build/install implementation](https://github.com/herdrdev/herdr/blob/v0.8.2/src/cli/plugin.rs), [runtime execution](https://github.com/herdrdev/herdr/blob/v0.8.2/src/app/api/plugins/runtime.rs).

## Declarative installation, updates, and runtime boundary

A future guarded task may use `herdr plugin install yankewei/herdr-focus-notify --ref f931db5090ded54086e365dfb8db896c3a3e1a05 --yes` **only when absent or explicitly reconciling a reviewed pin**. v0.8.2 accepts GitHub `owner/repo[/subdir]`, not arbitrary URLs; `--ref` is fetched directly (tag/branch/commit), omission fetches HEAD. Local `plugin link <path>` is the alternate source path and requires a separately built checkout. Install needs Git and Rust/Cargo; the manifest runs `cargo build --release`, **not `--locked`**, and downloads crate dependencies. There is no release-binary/checksum/signature verification path in this installer. The plugin has a committed crates.io lock and small serde/serde_json dependency graph, but future pin updates still require reviewing source, manifest, lock, and build inputs. [Installer](https://github.com/herdrdev/herdr/blob/v0.8.2/src/cli/plugin.rs), [Cargo inputs](https://github.com/yankewei/herdr-focus-notify/blob/f931db5090ded54086e365dfb8db896c3a3e1a05/Cargo.toml).

Repeated install always fetches/builds/replaces checkout, re-registers enabled=true, and updates installation timestamp, even for the same commit. No `plugin update` subcommand exists; reinstall is the update mechanism. Guard using installed metadata (`plugin list --json --plugin herdr-focus-notify` supports offline fallback): verify source owner/repo/ref/resolved commit, manifest availability and built executable, not mere presence/version. Detect a local link, foreign source, disabled state, or dirty/broken checkout and report rather than silently taking ownership. A source-metadata pin alone does not detect modified code/binary. Existing local links block remote replacement; another GitHub plugin with the same ID is not protected by equivalent source checking. Keep normal bootstrap non-upgrading; change reviewed pins/reinstall only through explicit update policy.

**Alerter provisioning, parent-verified:** installed mise 2026.9.1 failed the non-installing `mise bootstrap packages apply --dry-run brew:vjeantet/tap/alerter`: tap lacks `api/formula/alerter.json`, and this binary refuses brew-CLI fallback. This contradicts current [mise docs](https://mise.jdx.dev/bootstrap/packages/brew.html), which describe Ruby-DSL fallback. For this repository, use the existing macOS-scoped guarded `bootstrap:homebrew-packages` brew-CLI task for `vjeantet/tap/alerter`; do not claim native package support until an upgrade/retest proves it. Parent verified current [tap formula](https://github.com/vjeantet/homebrew-tap/blob/master/Formula/alerter.rb) is 26.5 with simple `bin.install`.

Keep only desired pins/tasks/research in dotfiles. Herdr owns `$XDG_CONFIG_HOME/herdr/plugins.json` (default `~/.config/herdr/plugins.json`), managed checkout under `plugins/github/<derived-id>`, separate config under `plugins/config/herdr-focus-notify`, and `$XDG_STATE_HOME/herdr/plugins/herdr-focus-notify` (default `~/.local/state/...`). Runtime contains learned bindings, generated mode-0700 scripts, icons, markers, and temporary notifier output. Do not symlink the entire Herdr directory to tracked configuration or commit these artifacts. Registry reloads mutable manifests; state/config survive managed checkout replacement and uninstall. Detached notifier scripts are not a durable managed service or automatically cancelled by disabling the plugin.
